# Shorepoint Technologies

A responsive agency website built with Next.js App Router, TypeScript, Tailwind CSS 4, and Lucide React. Contact inquiries are emailed server-side with the official Resend SDK. Shared Upstash Redis counters provide rate limiting across serverless instances; inquiry content is not stored in Redis.

## Local development

Use Node.js **22.x** and npm.

```sh
npm ci
cp .env.example .env.local
# Fill in your server-only credentials before testing the form.
npm run dev
```

Open http://localhost:3000. `.env.local` and other `.env*` files are ignored; only `.env.example` is tracked. Never commit actual credentials or prefix them with `NEXT_PUBLIC_`.

```sh
npm run lint
npm run typecheck
node --test tests/contact.test.cjs
npm run build
npm start
```

For a sandbox that blocks Turbopack’s internal worker port, use `npm run build -- --webpack`. The SDK and email credentials are used only at request time; build-time email credentials are not required.

## Resend setup

1. Create a Resend account and add a domain you own. Add the DNS records specified in the [Resend domain verification instructions](https://resend.com/docs/dashboard/domains/introduction), then wait for verification. A sending subdomain is an option. Do not assume a Gmail address or a customer's address is a verified sender.
2. Create a sending API key, ideally restricted to the verified domain. Set `RESEND_API_KEY` in your local/server environment.
3. Set `RESEND_FROM_EMAIL` to a **bare email address on that verified domain**. The server adds the display name `Shorepoint Technologies`. Do not put a display name or angle brackets in this variable.
4. Set `CONTACT_EMAIL` to the destination mailbox. The initial destination is documented in `.env.example`; change it for preview/testing as needed. There is no destination fallback in application code.
5. Provision an Upstash Redis database directly or through Vercel Marketplace. Set `UPSTASH_REDIS_REST_URL` to its HTTPS REST endpoint and `UPSTASH_REDIS_REST_TOKEN` to its standard **write-capable** token. See the [Upstash REST documentation](https://upstash.com/docs/redis/features/restapi). No Redis SDK is needed; the server uses authenticated HTTPS commands.

The Resend sender always comes from server configuration. The customer's validated email is used only as `replyTo`. Both plain-text and escaped HTML email bodies contain all five inquiry details. Success means Resend returned an email ID and accepted the message for delivery; it does **not** guarantee inbox arrival. Check the Resend dashboard for delivery, bounce, and spam outcomes. No confirmation email is sent to the customer.

## Vercel configuration

In **Project Settings → Environment Variables**, configure:

| Variable | Value |
| --- | --- |
| `RESEND_API_KEY` | Resend sending key |
| `CONTACT_EMAIL` | Destination mailbox |
| `RESEND_FROM_EMAIL` | Bare address on your Resend-verified domain |
| `UPSTASH_REDIS_REST_URL` | Upstash HTTPS REST endpoint |
| `UPSTASH_REDIS_REST_TOKEN` | Upstash write-capable REST token |

Apply the variables to Production and, if needed, Preview and Development. Use a separate destination mailbox for preview testing. Configure Node.js **22.x**, then redeploy: changing variables does not update an existing deployment. Vercel Marketplace may populate the Redis variables automatically; confirm the names match. Keep `RESEND_DEBUG` unset so provider debug logging cannot expose details.

After deployment, submit one approved test inquiry and check the destination inbox plus Resend's delivery logs. Confirm Reply addresses the customer. Test validation and honeypot rejection, and use a separate Redis database for deliberate rate-limit tests so testing does not exhaust the live budget. No live email has been sent during implementation.

## Contact endpoint and protections

`POST /api/contact` accepts JSON with string fields `name`, `business`, `email`, `projectType`, `description`, plus `website` (honeypot, must be empty) and `submissionId` (UUID v4 generated by the form). Project types must match `src/lib/inquiry.ts`.

- Limits: name 100, business 150, email 254, project type 80, description 20–5000 characters. The endpoint checks raw values, normalizes Unicode and whitespace, rejects control characters/header injection, and escapes HTML output. Unknown fields, non-string fields, arrays and malformed JSON are rejected.
- Request size is capped at **32 KiB**, based on streamed bytes even without a Content-Length header. Body reads time out after five seconds. Only JSON is accepted, and supplied cross-origin Origin headers are rejected.
- An atomic Redis Lua script allows **5 valid attempts per client address per 10 minutes** and **50 globally per hour**. Counters expire; no process-local fallback is used. The IP is HMAC-hashed with the Redis token before being used as a key. Token rotation resets those IP identities. Preview counters are separate from the main environment; separate databases per project/environment are recommended.
- Missing configuration, an unavailable store, or an untrusted production client address fails closed with a generic error. Rate-limit responses include `Retry-After`. Provider failures still count toward the attempt budget. Basic rate limiting and a honeypot are not a CAPTCHA or comprehensive protection against distributed abuse; Vercel Firewall controls can supplement them.
- Production IP identity uses Vercel's overwritten `x-vercel-forwarded-for` header only when `VERCEL=1`. On another production host, adapt the trusted-proxy policy before enabling delivery. Local development shares one rate-limit identity and still requires Redis. Do not manually set `VERCEL=1` outside Vercel to trust unverified headers.
- The client synchronously guards duplicate clicks, disables controls while sending, preserves input on failure, and reuses its submission identifier for retries of unchanged content. That identifier plus a server-side content digest forms a [Resend idempotency key](https://resend.com/docs/dashboard/emails/idempotency-keys). Resend retains keys for 24 hours; page reloads generate a new identifier. After an uncertain response, retry from the same page to retain the key.
- The UI displays success only after the provider accepts the email. Internal errors, provider IDs, and secrets are not returned to the browser. Server logs contain generic failures without inquiry contents. There is no inquiry database or authentication.

## Project structure

- `src/app`: root layout, SEO metadata, homepage, global styles, original SVG favicon.
- `src/app/api/contact/route.ts`: Node.js contact endpoint and Resend integration.
- `src/components`: reusable sections and client-side inquiry form/navigation.
- `src/lib/inquiry.ts`: shared types, limits, and validation.
- `src/lib/contact`: bounded request parsing, email formatting, shared rate limiting.
- `tests/contact.test.cjs`: isolated route tests using mocked Resend/network boundaries; no live emails or Redis writes.

The existing visual identity and motion remain intact. Most homepage sections are server components. Yellow Dog Coffee's Square integration remains labeled as planned; project visuals are illustrative concepts pending approved screenshots and client permission. Set canonical and social image URLs once the production domain and approved sharing image are available.
